# 本机执行改造方案

## 结论

改造量中等：图协议、服务端、调度器、Worker 适配器和数据结构可以复用，主要工作在 Windows 进程管理、CLI 发现、模型配置及持久化。推荐“本机 Codex 为默认，Docker 为可选”的双后端。0.5.0 先复用原 Web UI，当前运行方式仍为 Docker；本文件不是已经交付本机运行的声明。

## 现状对比

| 项目 | 本机模式 | Docker 模式 |
| --- | --- | --- |
| 首次环境 | 复用已安装 CLI，按需补少量工具 | Docker Desktop、应用镜像、Kali Worker 镜像 |
| 工具体积 | 随任务选择，可做得较小 | 当前完整 Worker 安装约 15.3 GB |
| 工具兼容 | Windows 工具或经适配的命令 | 原项目的 Linux 工具环境更完整 |
| 文件及进程 | 直接使用 Windows 路径、权限、进程 | 以容器目录与生命周期管理 |
| 运行环境隔离 | 专用目录与配置隔离，不等同于容器 | 每个项目一个容器，但挂载目录和网络仍共享指定资源 |
| 维护成本 | 需要发现 CLI 版本和工具缺失 | 统一镜像环境较容易复现 |

对已有 Codex、Claude Code、Pi 的开发电脑，本机模式更方便。对于需要大量 Linux 工具的学习任务，保留 Docker 有实际价值。界面的平滑程度与这两个执行模式无直接关系，由前端图渲染实现决定。

## 可以复用的部分

- `cairn/dispatcher/runtime/backend.py` 已定义统一执行后端接口。
- 调度器通过 `runtime.execution` 选择 `LocalBackend` 或 `ContainerManager`。
- Server/SQLite 的 Fact、Intent、Hint 协议与前端图无需改写。
- Codex/Claude Code/Pi 已有本地 CLI 驱动分支。

## 必须补齐的部分

1. **Windows 进程生命周期。** `LocalProcess` 当前使用 `os.killpg`、`os.getpgid` 和 `SIGKILL`；需要 Windows 的进程组或 Job Object 管理，保证超时、停止和退出时只终止本任务的进程树。CLI 发现要兼容原生 EXE 与 npm 的 CMD 包装入口，避免依赖不可靠的 shell 拼接。
2. **模型配置隔离。** 当前本地驱动使用 CLI 自己的配置，不会把桌面填写的 DeepSeek 配置直接接入。应提供“复用本机配置”和“应用专用 API 配置”两种明确入口。专用 Codex 配置放在统一存储根，通过 `CODEX_HOME` 等传递，避免覆盖用户现有的 Codex 登录和设置。
3. **持久化与过程日志。** 为本地后端接入阶段归档，统一保存节点编号、开始/结束时间、耗时、输出和取消原因。项目工作目录和 Codex 会话沿用 `output/<项目 ID>/{workspace,codex}`；本地后端现在缺少阶段归档入口。
4. **服务与调度器本地运行。** 把必要的 Cairn/Python 依赖打入程序或独立管理的小运行包，替代 Docker Compose 启动。管理服务就绪、端口冲突、调度器退出和运行日志；不能要求最终用户另装 Python。
5. **能力检测。** 本机 Codex、模型配置及基础工具分别检测，显示实际路径、版本和缺失项。缺少某种工具时给出明确反馈，按需安装或提示切换 Docker，而不是默认安装整个 Kali。

## 推荐实施顺序与验收

第一阶段让本机 Codex 使用其已有配置，完成一个不访问外部目标的文件任务，验证创建、执行、结论、停止、超时、进程树回收与文件落盘。

第二阶段加入应用专用 DeepSeek 配置和统一目录，确保不覆盖用户全局 CLI 设置。验证中文路径、空格路径、重启恢复和密钥不进入日志。

第三阶段增加本机/Docker 的界面选择、CLI 发现及工具能力检测。两种后端使用同一套任务过程图和节点日志，并对同一组协议任务验收。

最后处理可分发环境和资源清单。程序、托管依赖与用户数据分别更新，默认保留现有数据库、会话及任务产物。完整 Kali 工具镜像继续作为可选环境，避免每个桌面用户都必须下载它。
